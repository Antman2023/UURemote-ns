# v0.1.6 — 修复协商期间状态处理延迟

- 限制每轮信令读取最多 16 条、时间预算 8 毫秒；收到待处理的 RTC 回调或用户命令时提前让出。旧循环可能连续读取很长时间，使连接状态一直排队。
- 在检查心跳和连接超时前，再处理一次已排队的状态与命令，避免已收到连接进展却直接进入超时清理。
- 在公开 libnx TLS 读写入口显式设置非阻塞，保留暂无数据、部分读写和错误返回；使用链接包装，不访问 curl 的私有结构，也不修改 TLS 握手与证书验证。
- 日志增加慢速信令读取耗时和超时时刻的实际 Peer / ICE 状态，便于继续定位。

用户 v0.1.5 日志显示已发送 Offer、接收并应用 Answer，随后持续应用远端候选，但主循环未及时处理后续 RTC 状态，最终超时。DTLS 的 EOF 错误出现在断开之后，不能将它直接当作最初失败原因。该日志支持修复事件处理延迟，但尚不足以确认真机链路的所有问题均已解决。

验证通过：Switch ARM64 编译；协议、短信参数、后台线程、日志脱敏、信令洪泛 / 取消与 TLS 服务模拟共 6 项测试；最终二进制 TLS 读写包装调用检查；NRO 版本、ZIP CRC、包内文件和 SHA256 检查。TLS 服务测试使用模拟接口，无法替代 Horizon 真机网络验证。

退出旧程序后，将 NRO 覆盖到 SD 卡根目录下的 `switch/UURemote-ns/UURemote-ns.nro`。启动确认首页为 `v0.1.6`，再次连接；如果仍失败，请提供这次生成的 `connection.log`，启动标记应为 `app-start-0.1.6`。
